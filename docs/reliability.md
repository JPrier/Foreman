# Long-running tasks: recovery, evidence, and cost

Foreman stores the original objective and every follow-up verbatim. The director receives those requirements, a ledger, assignment states, a report catalog, and recent summaries. Full worker reports are stored under the task directory and can be requested by ID using `retrieve_reports` in a director decision, or as an excerpt using an ID and zero-based `start`/`end` character offsets. Retrieval and offsets are logged and the requested reports appear in the next decision; the current action is deferred. If requirements, ledger, or requested reports cannot fit the configured context limit, the task stops with an error rather than silently dropping them. Increase `director.max_context_chars`, request smaller excerpts, or use a model with a larger context. A provider context-window error also stops the task with the error preserved.

The director maintains outcomes, delivery steps, findings and blockers via `ledger_updates`. Entries have an ID, kind, description, status, optional owner and reason, and worker evidence references. Objective and follow-up text cannot be changed. An entry can be resolved only with a successful worker report; `finish` becomes `partial` while any ledger entry lacks valid evidence, a finding remains open, an assignment is failed, interrupted, blocked, queued or running, or the director has not explicitly reviewed requirements and declared whether delivery is needed. Declared delivery also requires a delivery entry. The ledger is a structured record of model judgments, not an independent verification system: it cannot prove that the director decomposed every natural-language request, correctly classified delivery, that a worker actually ran a check, or that a report's claims are true. For important changes, dispatch a separate reviewer and inspect artifacts directly. An explicitly unresolved hypothesis or deferred risk prevents `done` and remains visible as partial.

Evidence can list absolute artifact paths and their SHA-256 hashes. Ask workers to include those values in their report. Evidence for code can instead include a `repositories` mapping from the checkout path to the `commit` and `fingerprint` emitted by `smart-coder fingerprint PATH`; the report must include all three values. The fingerprint includes HEAD, index, tracked changes, and untracked non-ignored file contents. The gate recomputes it before completion and treats a mismatch or unavailable path as stale. Record the fingerprint during the check; this only ties the report to the recorded snapshot, and does not prove the check ran or that the snapshot was atomic. Ignored files, external services, dependencies, remote branches and changes outside the declared scope are not covered. Unscoped evidence is invalidated by later mutating dispatches or follow-ups. Re-run checks after relevant state changes, and independently verify remote delivery when requested.

Assignments are saved before execution; per-worker JSON event streams are appended as OpenCode emits them, and full final reports and accounting are saved as each worker finishes. An operating-system lock prevents concurrent coordinators for the same task. PID, process creation identity and session ID are saved as available. On `status` or `continue`, Foreman checks whether the coordinator and known worker processes still exist; a lost dispatch becomes interrupted. If a known worker might still be alive, recovery is blocked until it exits. Process IDs can be reused and identity can be uncertain, so checks are conservative. There is a small gap between process creation and saving its PID, and the harness cannot enumerate unknown descendants or prove side effects did not occur. Inspect the event log, files and external services before retrying. A separate successful worker report can reconcile a failed, blocked or interrupted assignment via `resolved_assignments`; this is still a report, not independent proof.

Routing uses `worker.model`, `worker.medium_model` and `worker.high_model` for routine, medium and high difficulty. A retry of a failed or interrupted routine assignment escalates to medium. All three default to the same inexpensive model; configure distinct OpenCode model IDs if escalation is desired. Measure retries, outcomes, review quality and total effort, not model prices alone. `worker.long_assignment_seconds` and `worker.expensive_assignment_usd` surface long or costly assignments. Director records include context characters, duration, reported usage/cost and a preflight reserve; worker records include model, duration, reported tokens when available, cost, completeness and retry linkage. Unknown values stay unknown. OpenCode subscription cost is not an actual dollar charge. Optional `director.equivalent_input_per_million`, `equivalent_output_per_million`, `equivalent_cache_read_per_million` and `equivalent_cache_write_per_million` configure an illustrative API-equivalent estimate; all rates and complete separate token categories must be available or the estimate remains unknown. This calculation assumes the provider reports input, output, cache reads and cache writes as non-overlapping categories; verify that convention and the chosen rates yourself. It does not represent a subscription charge or remaining quota.

`limits.premium_budget_usd` preflights direct OpenRouter director calls. `limits.worker_budget_usd` checks the sum of reported worker charges before a batch and between sequential assignments. Both are best effort: unknown or late charges, in-flight requests and parallel workers can exceed thresholds, and subscriptions cannot be measured in dollars here. Use provider-side limits where available. Interrupted work may have unreported charges; the accounting flag remains incomplete after recovery. Run `status` to see assignment states, elapsed time, ledger progress and recent warnings. Budget exhaustion preserves the task and can be resumed after configuration changes.
